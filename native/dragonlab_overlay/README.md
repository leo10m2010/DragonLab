# DragonLab passive native overlay

Rust/Win32 GDI prototype for the manual guide. It does not inspect game state,
inject input, register shortcuts or activate the game. The host supplies projected
geometry. The DLL is independent of Python and Tk.

## Build and checks

```powershell
cargo test --locked -- --test-threads=1
cargo clippy --locked --all-targets -- -D warnings
cargo build --release --locked
```

The Windows DLL is `target/release/dragonlab_overlay.dll`. The pinned dependencies
and `Cargo.lock` are part of this crate. Tests include coalescing, unchanged-scene
deduplication, layered/click-through/no-activation flags, no foreground-window
change and GDI resource cleanup. `target/overlay-qa.bmp` is generated by a test
that draws only a synthetic scene to its own private bitmap; it is not a desktop
capture. This verifies rendering, not in-match alignment or physics.

## C ABI

- `int32_t dl_overlay_update_json(const uint8_t *input, size_t len)` parses a full
  UTF-8 scene. Returns `0` when accepted, `1` when unchanged, negative on failure.
  Input bytes are copied/parsed during the call and need not remain alive.
- `void dl_overlay_close(void)` stops and joins the message thread. Idempotent.
  Call before unloading the DLL; updates can restart it after a close.
- `uint32_t dl_overlay_status(void)` bit 0 is thread alive, bit 1 is window visible.
- `char *dl_overlay_status_json(void)` returns owned UTF-8 diagnostics: running,
  visible, submitted, painted (latest sequence), coalesced, transparent,
  no_activate, layered and screen box. Release once with
  `void dl_overlay_string_free(char *)`.

Only one overlay exists per loaded DLL. Update and close serialize through a
mutex; the message thread owns all paint resources. There is one replaceable
pending scene and a blocking message loop, no polling timer. A compatible bitmap
is reused until dimensions change. Equal scenes do not wake or repaint the thread.

## Scene

```json
{
  "box": [10, 20, 810, 620],
  "viewport": [800, 600],
  "visible": true,
  "planned": [[[100, 400], [300, 180], [700, 400]]],
  "observed": {"shot-1": [[100, 400], [300, 182], [702, 403]]},
  "players": [{"x": 700, "y": 400, "selected": true, "label": "ENEMIGO 1"}],
  "annotations": [{"points": [[450, 0], [450, 516]], "color": "#D69CFC", "width": 1, "label": "Mirror", "x": 450, "y": 43}],
  "style": {"color": "#77F59C", "observed_color": "#C1E6CB", "width": 3, "font_size": 11},
  "guide": {"bar": [30, 570, 770, 570], "power": 205, "maxPower": 400, "label": "SUELTA EN 205 / 400", "visible": true, "measured": true}
}
```

Planned/observed paths, players and annotations are already projected to viewport
coordinates. `null` separates strokes without bridging a gap; every supplied
vertex is retained. Player `hero`, `selected`, `dead` flags and `label` are optional.
`guide.bar` is in screen coordinates; `updating`, `blocked`, `measured` are optional.
The passive window covers the union of the field and power bar. Field graphics
are clipped above the control region at `516 / viewportHeight`, matching the Tk
guide. The bar and label may extend outside the field. Offscreen players receive
an edge arrow and label. Geometry uses physical pixels with per-monitor awareness
scoped to the overlay thread.

Limits: 8 MiB JSON, 200,000 vertices, 512 paths per set, 256 players, 512
annotations, 2,048 characters per label, window dimensions at most 16,384 pixels.
Invalid scenes are rejected instead of replacing a valid frame. The raster GDI
polyline implementation uses solid round pens, not spline smoothing. Font edges
are antialiased against their opaque rounded label background. The prototype does
not implement independent physics or weather interpretation; annotations must
come from the host.

Win32 contracts checked against Microsoft's [layered-window documentation](https://learn.microsoft.com/en-us/windows/win32/winmsg/window-features)
and [`SetLayeredWindowAttributes`](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-setlayeredwindowattributes).
